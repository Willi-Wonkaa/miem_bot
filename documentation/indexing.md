# Индексатор и исходные данные

Точка входа — `python -m app.rag.indexing`; в Compose это контейнер `indexer` из профиля `index`. Он читает ZIP/Excel и пишет в общий с RAG volume `index-data`. В работающем приложении документы не распаковываются.

## Входные файлы

- `data/raw/MIEM_knowledge_base_unified.zip` обязателен. На VPS источник находится в `/opt/miem-bot/shared/raw/` и подставляется через `compose.server.yaml`.
- В архиве должен быть ровно один `manifest.json` с массивом `documents`. У каждого документа есть уникальный `document_id`, `file` относительно manifest и `title`; `category` необязателен. Поддерживаются DOCX, TXT и PDF с текстовым слоем. OCR нет.
- `all_links.txt` внутри архива необязателен. В строке ожидается описание и HTTP(S)-ссылка.
- `data/raw/HSE_Answers_RU.xlsx` необязателен. В первой вкладке нужны колонки «Основной вопрос», «Варианты вопроса на русском», «Ответ на русском». Варианты разделены переводами строк.

Распаковка проверяет пути и символьные ссылки, ограничивает суммарный размер 512 MiB. `parsing.py` извлекает блоки текста, `chunking.py` собирает фрагменты. Модель `intfloat/multilingual-e5-base` кодирует документы с префиксом `passage: `, запросы — с `query: `. Векторы нормализуются; FAISS использует скалярное произведение.

## Ход работы

`IncrementalIndexer` сначала разбирает документы в отдельных процессах, затем обрабатывает файлы параллельными рабочими потоками с общей моделью E5. Короткие файлы идут первыми. Для каждого документа сохраняются чанки и батчи векторов. Первый успешный документ публикуется сразу; далее новая версия появляется примерно каждые `INDEX_PUBLISH_PERCENT` процентов корпуса. FAQ и ссылки добавляются после документов.

| Путь в `index-data` | Содержимое |
| --- | --- |
| `work/<build_hash>/` | Распакованный источник и текущий `progress.json` |
| `checkpoints/<hash>/` | Чанки и готовые батчи эмбеддингов документа |
| `extras/` | Общие для поколений данные FAQ и ссылок |
| `<generation>/` | FAISS, JSON фрагментов/FAQ/ссылок, векторы и метаданные |
| `CURRENT` | Имя опубликованного поколения |
| `WRITER.lock` | Блокировка второго индексатора |

Изменённый документ пересчитывается по хешу содержимого, метаданных, модели, точности и кода парсинга. Если процесс остановлен, сохранённые батчи переиспользуются. Публикация записывает готовое поколение до смены `CURRENT`. Ошибки отдельных файлов оставляют частично доступную базу, но поколение не помечается полностью готовым.

Настройки скорости и ресурсов — в [`.env.example`](../.env.example): `INDEX_PARSE_WORKERS`, `INDEX_WORKERS`, `EMBED_BATCH_SIZE`, `EMBED_QUANTIZE`, `INDEX_PUBLISH_PERCENT`. Изменение модели, точности или парсера требует пересчёта соответствующих данных. Прогресс виден через `/index` RAG API и команду `/index` служебного бота.
