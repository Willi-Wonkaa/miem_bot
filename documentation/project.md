# Проект

Путь запроса: Telegram → bot → RAG API → готовый ответ или hybrid retrieval → Polza → Telegram.

| Файл / каталог | Ответственность | Блоки Colab |
| --- | --- | --- |
| `app/config.py` | Настройки из `.env`, проверка обязательных токенов | API и Telegram credentials |
| `app/rag/parsing.py` | DOCX, таблицы, TXT, PDF; очистка текста | 4 |
| `app/rag/chunking.py` | Структурные фрагменты с перекрытием | 5 |
| `app/rag/indexing.py` | Распаковка базы, E5, сохранение FAISS, ссылок и FAQ | 3, 6, ссылки, Excel |
| `app/rag/retrieval.py` | Отдельные BM25 для документов и FAQ; RRF, ссылки, соседние чанки | 9, 11, готовые ответы |
| `app/rag/prompts.py` | Исходные системные промпты | Rerank, answer, rewrite |
| `app/rag/pipeline.py` | FAQ → rewrite → retrieval → Qwen rerank → Qwen answer | 10, 12, история |
| `app/rag/api.py` | Внутренний HTTP API, авторизация, ограничение параллелизма | Новый серверный слой |
| `app/telegram/` | Polling, форматирование, Redis-история, блокировка повторных запросов | Бот |
| `app/service/`, `app/telemetry.py` | Служебный Telegram-бот, уведомления, SQLite-счётчики и кнопки | Новый мониторинг |
| `app/logging_setup.py`, `app/host_monitor.py` | TXT-логи, Docker-статусы, лимиты ресурсов индексатора | Новый мониторинг |
| `data/raw/` | Архив базы: 205 документов; Excel с готовыми ответами | Загрузки Colab |
| `scripts/` | Импорт данных, подготовка VPS, деплой | Замена ручного запуска |
| `tests/` | Индексация, retrieval, API, Telegram; без внешних токенов | Замена sanity-прогонов |

Контейнеры: `service`, `bot`, `rag`, `redis`. `indexer` — одноразовая задача через профиль `index`.
Volumes: `index-data` — версии индексов, `model-cache` — E5, `redis-data` — история.
Снаружи порты не публикуются. Бот использует long polling.

Исправлено: FAQ больше не перезаписывает BM25 основной базы; проверка cosine относится
к выбранному FAQ-ответу; пустые/нетекстовые сообщения обработаны; история учитывает чат и пользователя.
Сохранены пороги FAQ и ссылок, агрегация документов, соседние чанки и язык текущего вопроса.
Английские вопросы проходят через RAG, поскольку готовые ответы в Excel только на русском.
Colab upload, `nest_asyncio`, отладочные распечатки, benchmark и judge в production не включены.

## Подробный путь пользовательского запроса

1. `app/telegram/bot.py` принимает обновления Telegram через long polling.
   Нетекстовые сообщения и слишком длинные вопросы обрабатываются отдельно.
   История изолирована по чату и пользователю; Redis-блокировка не допускает два
   одновременных вопроса в одной сессии. Освободить блокировку может только её владелец.
2. Бот отправляет вопрос и последние 10 записей истории в `POST /answer` с внутренним
   Bearer-токеном. FastAPI проверяет авторизацию, содержимое и размер вопроса/истории.
3. Если рабочая версия ещё не загружена, API вызывает генератор без материалов базы
   и возвращает маршрут `fallback`, без источников. Ответ ограничен достоверными
   сведениями и рекомендацией уточнить неизвестные данные. `/health` при этом доступен:
   готовность HTTP API и готовность базы — разные признаки.
4. Для готового индекса API фиксирует ссылку на неизменяемый snapshot и получает слот
   из семафора. По умолчанию одновременно обрабатываются 2 запроса; ожидание слота
   ограничено 5 секундами, при перегрузке возвращается HTTP 429.
5. `Pipeline.answer` сначала ищет готовый русский FAQ-ответ. Отдельные векторные
   и BM25-оценки объединяются через RRF; оба порога относятся к одному кандидату.
   Успешный FAQ-ответ не вызывает LLM. Английский вопрос проходит через RAG.
6. При наличии истории LLM переписывает вопрос в самостоятельный запрос.
   Retrieval объединяет до 60 результатов FAISS и до 60 результатов BM25;
   веса RRF — 1 и 0.9, константа ранга — 60. Из них выбираются до 40 кандидатов.
7. LLM reranker оценивает кандидатов. Контекст собирается по документам, с соседними
   чанками; максимум 9 чанков и 18 000 символов. Отдельно выбираются до 2 ссылок
   с cosine выше `LINK_THRESHOLD` (по умолчанию 0.75).
8. Polza генерирует ответ по исходным промптам, API возвращает ответ, источники,
   маршрут, токены, длительность и покрытие базы. Ошибки генерации становятся HTTP 502.
9. Бот форматирует ответ для Telegram, сохраняет успешный диалог в Redis
   и обновляет счётчики. При неполной базе отдельно отправляет короткое предупреждение
   об обновлении; прогресс и имена файлов в ответ не включаются. История содержит 5 пар
   и живёт 24 часа после последнего ответа.

## Индексация и сохранённые данные

Архив должен содержать ровно один `manifest.json`, документы с уникальным `document_id`
и путями внутри распакованной базы. Распаковка запрещает выход за каталог, символические
ссылки и общий распакованный размер свыше 512 MiB.
Парсеры сохраняют заголовки, абзацы и строки таблиц DOCX, извлекают текст TXT/PDF.
PDF без текстового слоя не распознаётся: OCR в проекте нет.

Чанкер использует блоки примерно до 1600 символов; длинный блок делится на части
до 1400 символов. Между чанками сохраняется последний короткий блок до 350 символов.
Для короткого документа парсер создаёт один чанк, если обычный чанкер ничего не оставил.
Модель E5 получает префикс `passage: ` для документов и `query: ` для вопросов;
векторы нормализуются, FAISS использует скалярное произведение.

`IncrementalIndexer` распараллеливает только парсинг. Вычисление эмбеддингов происходит
в главном процессе, поэтому каждый parser worker не загружает свою модель.
Рабочие каталоги, checkpoint и публикации лежат в `index-data`:

| Путь | Содержимое |
| --- | --- |
| `work/<build_hash>/` | Распакованный архив и текущий `progress.json` |
| `checkpoints/<hash>/chunks.json` | Результат парсинга документа |
| `checkpoints/<hash>/batch-*.npy` | Сохранённые батчи эмбеддингов |
| `checkpoints/<hash>/vectors.npy` | Полный набор векторов документа/дополнительных данных |
| `extras/` | FAQ/ссылки, общие для публикаций; переиспользуются через hard links |
| `<generation>/` | FAISS, чанки, FAQ/ссылки, `extras.npz`, метаданные |
| `CURRENT` | Указатель на последнюю опубликованную версию |

Хеш документа включает его содержимое, метаданные, модель, точность и код парсинга.
Изменение одного документа не требует заново вычислять неизменённые документы.
Перед сменой `CURRENT` все файлы версии записываются и синхронизируются;
writer lock допускает одного писателя. RAG загружает новый snapshot в другом потоке
и заменяет ссылку только после успешной проверки. При повреждённой публикации
остаётся предыдущий рабочий snapshot.

## Запуск и проверка системы

`scripts/start.py` использует только стандартную библиотеку Python и существующую
GitHub-аутентификацию. Он запускает `workflow_dispatch` с уникальным `request_id`,
находит именно свой workflow и проверяет итог **job deploy**, а не только общий CI.
По умолчанию выбран `index`; `prepare` и `deploy` сохраняют отдельные назначения.

Pipeline тестирует исходники, собирает bot/rag-образы и упаковывает проверенный commit
через `git archive`. `remote_deploy.py` передаёт архив по SFTP с проверкой SSH host key.
`deploy.sh` создаёт release, связывает его с shared-данными, собирает образы на VPS,
запускает служебного бота, монитор и остальные компоненты.
При ошибке до переключения `current` выполняется восстановление предыдущего release.
Ошибка индексации после активации сохраняет уже запущенные сервисы и частичную базу.

`app.rag.smoke` проверяет `/health`, авторизованный `/index`, HTTP 401 при неверном
токене и, по параметрам, первый доступный документ/полный индекс/реальный ответ.
Окончательная проверка `index` обнаруживает ситуацию, когда индексатор завершился с
exit code 0, но отдельные файлы не обработались и metadata содержит `complete=false`.

## Практические ограничения текущей реализации

- Offline-тесты используют детерминированный `FakeEmbedder` и имитации Telegram/LLM.
  Они проверяют алгоритмы и поведение API, но качество E5/Qwen и реальные токены
  подтверждаются серверным запуском и ручной оценкой ответа.
- Служебный бот допускает подписку любого пользователя в личном чате; whitelist отсутствует.
  Это текущее поведение `create_dispatcher`, а не ограничение Telegram.
- Монитор, запускаемый deployment, работает через `nohup`. Автозапуск этого процесса
  после перезагрузки VPS таким способом не обеспечивается; отдельно есть скрипт
  установки systemd-сервиса, но основной pipeline его не использует.
- Монитор использует резерв по умолчанию 1 CPU/3 GiB RAM и ограничивает динамический
  лимит памяти индексатора 4 GiB. Его `docker update` может изменить исходные
  `INDEX_CPU_LIMIT`/`INDEX_MEM_LIMIT` из Compose: фактический лимит смотреть в статусе.
- Индексатор сохраняет старые поколения и checkpoints; автоматической очистки нет.
  Для долгой эксплуатации нужны бэкап volumes и контролируемая очистка старых данных.
- `app/rag/check_index.py` и тесты `test_deploy.py` проверяют полный индекс как утилиту;
  основной deployment допускает пустой/частичный индекс и этим старым валидатором
  запуск не блокирует. `app/rag/progress.py` содержит прежний observer и в текущем
  `IncrementalIndexer` не используется.
