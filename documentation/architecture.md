# Архитектура

Система состоит из четырёх постоянно работающих контейнеров (`service`, `redis`, `rag`, `bot`), разового контейнера `indexer` и процесса мониторинга на хосте. Их состав и зависимости заданы в [`compose.yaml`](../compose.yaml).

```text
Пользователь → Telegram → bot → POST /answer → rag → Polza API
                            ↕                  ↕
                          Redis          опубликованный индекс
                                             ↑
                    ZIP + Excel → indexer → index-data

service ← SQLite телеметрии → bot / rag / indexer
   ↑
host_monitor → Docker status и лимиты indexer
```

## Как получается ответ

1. `app/telegram/bot.py` принимает текст через long polling. История последних пяти пар сообщений хранится в Redis по паре «чат + пользователь». Redis также блокирует второй одновременный запрос в этой сессии.
2. Бот вызывает `POST /answer` внутреннего FastAPI с Bearer-токеном. API проверяет токен, ограничивает длину вопроса и число одновременных запросов.
3. Пока индекс не опубликован, `Pipeline` вызывает Polza без материалов базы (`route=fallback`). Когда индекс готов, сначала проверяется русский FAQ из Excel (`route=faq`, без вызова LLM). Остальные вопросы идут по документам (`route=rag`).
4. Для RAG поиск объединяет FAISS и BM25; Polza переписывает вопрос с учётом истории, ранжирует фрагменты и формирует ответ. Список названий использованных документов возвращается вместе с ответом.
5. Бот отправляет ответ в Telegram, сохраняет успешный обмен в Redis и записывает счётчики. Сейчас он также пишет диалог и оценки в отдельную SQLite-базу; условия работы этой функции — в [описании бота](telegram.md).

RAG API не публикует порт наружу. `/health` показывает готовность процесса, а поле `index_ready` — наличие загруженной базы; это разные состояния. `/index` и `/answer` требуют `RAG_API_TOKEN`.

## Как обновляется база

`indexer` распаковывает ZIP, парсит документы, создаёт фрагменты и эмбеддинги, затем публикует версию в `index-data`. Файл `CURRENT` указывает на опубликованное поколение. `rag` проверяет его каждые `INDEX_RELOAD_SECONDS` секунд и загружает новую версию в фоне. Уже начатый запрос заканчивается на прежней версии. Промежуточные результаты индексатора сохраняются в `checkpoints/`; повторный запуск продолжает работу. Подробности — в [индексации](indexing.md).

## Где хранится состояние

| Хранилище | Что в нём |
| --- | --- |
| `redis-data` | История диалогов для контекста LLM и блокировки сессий |
| `index-data` | Поколения индекса, `CURRENT`, рабочие файлы и checkpoints |
| `model-cache` | Загруженная модель E5 |
| `monitor-data` | SQLite телеметрии: состояния, события, подписки и счётчики |
| `shared/raw/` на VPS | Исходный ZIP и Excel |
| `shared/logs/`, `shared/host/` | Текстовые логи и файлы хостового монитора |

Архив диалогов (`app/transcripts.py`) использует отдельный SQLite-файл по `CONVERSATION_DIR`. Compose монтирует общий каталог в `bot` и `service`; на VPS это `/opt/miem-bot/shared/history/`. Данные Redis и этот архив не следует путать. Подробности — в [переписках и оценках](history.md).
