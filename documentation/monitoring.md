# Логи и служебный бот

`SERVICE_BOT_TOKEN` — токен отдельного бота в серверном `shared/.env`.
Каждый администратор активирует его через `/start` в личном чате. Белого списка нет.
Основные кнопки: статус, индексация, запросы, обновление текущего экрана, уведомления.
Переключатели уведомлений находятся на отдельном экране; включённые отмечены 🟢, выключенные 🔴.
Команды: `/status` — общий статус; `/index` (или `/progress`) — файлы, процент,
весь объём, форматы, общий прогресс по тексту/FAQ/ссылкам, состояние индексаторов и ETA;
`/requests` (или `/stats`) — запросы к `/answer` за 1/5/30 минут,
общий счётчик, обработанные запросы и ошибки. Прогресс и запросы доступны и отдельными кнопками.
Настройки независимы для каждого чата и сохраняются после рестарта.

Сообщения считаются за 1/5/30 минут и с последнего запуска основного бота.
Автоматически приходят анализ с оценкой времени, успешный старт рабочих индексаторов
и отдельное уведомление о полном завершении. Детальная статистика запросов и сообщения
о файлах по умолчанию выключены; их можно включить на экране уведомлений.
Для старых подписок эти два подробных потока выключаются при миграции интерфейса;
остальные настройки сохраняются. Завершение включено отдельно от промежуточного прогресса.
Счётчики запросов к API сохраняются в SQLite независимо от перезапуска ботов;
неверная авторизация и запросы healthcheck в них не входят.
Статус показывает Docker state/health, время старта, компоненты и прогресс индексатора.

Логи UTF-8: `/opt/miem-bot/shared/logs/*.txt`; ротация по 10 MiB, 5 резервных файлов.
`indexer.txt`, `bot.txt`, `rag.txt`, `service.txt`; логи процессов парсинга — `parser-<pid>.txt`.
Монитор deployment пишет `host-monitor.txt` и `monitor-console.txt` в `shared/host/`.
Логируются этапы, длительность, ошибки, файлы и расход токенов LLM; ключи маскируются.
Тексты вопросов/ответов и история целиком в логи не записываются.

`monitor-data` — SQLite: события, счётчики, подписки и настройки кнопок.
Монитор собирает состояния Docker и меняет лимиты индексатора под deployment-учётной записью.
Pipeline сам запускает `scripts/start_monitor.sh`; ручная установка на сервере не требуется.
У контейнеров нет Docker socket. Данные статусов монтируются в служебный бот только для чтения.
Резерв: минимум 1 CPU и 3 GiB RAM для ОС и остальных процессов; индексатору — до 80% остатка.
При нехватке RAM запрашивается остановка, чтобы не уменьшать лимит ниже рабочего набора памяти.
После восстановления ресурсов монитор возобновляет контейнер из checkpoints без Actions.
Нехватка CPU приводит к снижению квоты; остановка по памяти учитывает рабочий набор
без reclaimable file cache. В лог записываются memory.current, working set, бюджет и
свободная RAM. До остановки монитор передаёт индексатору причину через readonly-каталог
`/data/host`; deploy так же сообщает о плановом обновлении версии.
Сообщение о паузе содержит причину и сохранённый общий прогресс, без повторных
отбивок `indexer: interrupted` и `container exited`.

Порядок старта: `service` → `redis`/`rag` → `bot`; индексатор тоже ждёт готовности `service`.
Команды основного бота: `/index`, `/index_watch`, `/index_unwatch`, `/reset`.
Файлы и промежуточные батчи сохраняются сразу. Первый файл публикуется немедленно, остальные — каждые 5%.
RAG загружает новые версии в фоне; активные запросы завершаются на своей версии индекса.
